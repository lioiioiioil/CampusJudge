# Автоматическая проверка: план и контракт

Следующий этап сохраняет Go API, JSON-файл и один процесс сервера. БД и CI не
добавляются. Изменения публикуются отдельными проверенными коммитами.

1. Изолированный исполнитель: Linux-контейнеры в Docker, компиляция и запуск с
   ограничениями времени, памяти, процессов, вывода и сети. На macOS — отдельная
   Linux VM. Исходники никогда не выполняются процессом API или на его хосте.
2. Сохранённая очередь: отправка сразу возвращает ID, затем состояния «в очереди»,
   «проверяется» и итоговый вердикт. Перезапуск продолжает незавершённые задания.
   Ошибка инфраструктуры отличается от ошибки решения и не добавляет штраф.
3. Шаблоны полных программ для языков, включая `main` для C++; переключение языка
   сохраняет черновик. Результат автоматически обновляется без перезагрузки.
4. Светлая и тёмная темы, рабочая область с условием слева и редактором справа.
   Ориентир — [публичный экран задачи LeetCode](https://leetcode.com/problems/two-sum/description/),
   со своей реализацией и без чужих ассетов.
5. Реальные проверки AC/WA/CE/RE/TLE/MLE и ограничений контейнера, затем полный
   сценарий через API и браузер. Обновление инструкций запуска по итогам.

Первый набор автоматических исполнителей: C++, C, Python, Go, Java и JavaScript.
Остальные языки можно отправлять для ручной проверки. В API у каждого языка явно
указано, доступна ли автоматическая проверка. Тесты идут в порядке: примеры,
затем скрытые. Сравнение — последовательность разделённых пробельными символами
токенов; специальные проверяющие программы и интерактивные задачи пока не входят.

Скрытые входы и ожидаемые ответы не возвращаются клиенту. Пользователь получает
вердикт, количество пройденных тестов, номер первого неуспешного и ограниченный
вывод компилятора. Ручное решение преподавателя имеет приоритет над поздним
результатом worker.

Docker daemon и образ должны быть доступны до включения автоматического режима.
Контейнер не получает каталог API, рабочий JSON, домашний каталог, Docker socket
или сеть. Применяются ограничения из
[Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/)
и [Docker security](https://docs.docker.com/engine/security/).
Для публичного сервиса нужен выделенный исполнитель; локальные ограничения не
являются обещанием изоляции уровня Codeforces.

## Локальная настройка

В Linux нужен Docker с cgroup v2. В macOS можно использовать Docker Desktop либо
отдельный профиль Colima. Вариант Colima не меняет глобальный Docker context и
не подключает к VM домашний каталог:

```sh
brew install colima docker
colima start campusjudge --vm-type vz --arch aarch64 --runtime docker --cpus 4 --memory 4 --disk 20 --mount none --ssh-agent=false --ssh-config=false --activate=false --template=false
export DOCKER_CONTEXT=colima-campusjudge
docker build -t campusjudge-runner:local -f judge/Dockerfile .
go run ./cmd/campusjudge
```

Команда выше предназначена для Apple Silicon. На Linux или с Docker Desktop
дополнительный Colima-профиль не нужен. Образ собирается из корня репозитория;
`.dockerignore` ограничивает контекст файлами supervisor и его протокола.

Если CLI сообщает, что BuildKit недоступен без buildx, можно установить плагин
buildx либо выполнить ту же сборку с `DOCKER_BUILDKIT=0`. Образ не публикуется
в registry; скачиваются только базовые образы и пакеты компиляторов при сборке.
Во время проверки сеть контейнеров отключена.

## Границы исполнения

Каждая компиляция и каждый тест получают отдельный контейнер: read-only root,
пустую сеть, ограниченные tmpfs, память без swap, CPU, число процессов, размер
файлов и общий stdout/stderr. Компиляция ограничена 60 секундами и 1 ГБ,
исходник — 128 КиБ, вывод решения — 1 МиБ, диагностика компилятора — 16 КиБ.
Тест получает лимиты задачи. Подготовка контейнера не входит в измеренное время
исполнения; клиенту показывается наибольшее время одного теста.

Доверенный PID 1 получает только SETUID, SETGID и KILL: запускает компилятор и
решение как uid/gid 65534 без capabilities и может остановить их по таймауту.
Отдельный watchdog работает даже при обрыве API до передачи stdin. Supervisor
не передаёт свой протокол в stdout дочернего процесса. Программа получает только
вход текущего теста; ожидаемый ответ остаётся в Go API и сравнивается там.

Пакет артефактов передаётся через память с пределом 32 МиБ. Рабочих bind mounts,
постоянных volumes и Docker logs у sandbox нет. Контейнеры удаляются после
завершения и отмены; после аварийного kill API watchdog ограничивает время жизни
контейнера, но остановленные метаданные можно удалить вручную по метке
`campusjudge.sandbox=true`.

Очередь однонаправленная: `queued` → `running` → `done` или `error`. Она
сохраняется атомарно с посылками. HTTP-запрос не ждёт компиляции и выполнения;
браузер читает актуальное состояние примерно раз в 1,2 секунды, пока есть активные
проверки. При остановке процесса незавершённая задача может быть выполнена ещё
раз; сеть и внешние эффекты решения недоступны. Старые ручные посылки не
запускаются автоматически. Преподаватель может проверить их по-прежнему.

Если Docker или образ недоступны, автоматический режим не запускается. Для
осознанного ручного режима используйте `-judge manual`. Ошибка исполнителя во
время работы даёт `judge_error`, а не неверный ответ; преподаватель видит посылку
и может выставить ручной результат.
