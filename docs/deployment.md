# CampusJudge: готовый контейнерный выпуск

Готовый архив из [GitHub Releases](https://github.com/lioiioiioil/CampusJudge/releases)
содержит образы приложения, исполнителя шести языков и PostgreSQL, настройки
запуска и контрольные суммы. На сервере не нужны Go, Node.js и сборка проекта.
После загрузки архива образы можно установить без обращения к registry.

Проверяемый вариант — Docker Engine на Linux с cgroup v2 и Docker Compose v2.
Архив `linux-amd64` предназначен для x86-64, `linux-arm64` — для ARM64;
используйте архитектуру Docker-сервера. Наличие ARM64- или AMD64-архива
определяется конкретным выпуском. Podman в этом варианте не проверен.

## Установка из готового архива

Скачайте архив нужной архитектуры и соседний файл `.sha256` из одного выпуска.
Пример для `v0.1.0` и Linux x86-64:

```sh
sha256sum -c campusjudge-v0.1.0-linux-amd64.tar.gz.sha256
tar -xzf campusjudge-v0.1.0-linux-amd64.tar.gz
cd campusjudge-v0.1.0-linux-amd64
./load-images.sh
./init-env.sh
docker compose up -d --wait
```

`load-images.sh` проверяет контрольную сумму вложенного архива и архитектуру
Docker-сервера, затем загружает три образа. `init-env.sh` создаёт `.env` с правами
`0600` и разными случайными паролями БД и преподавателя. Существующий `.env`
скрипт не заменяет. Образы имеют теги конкретного выпуска; Compose использует
локально загруженные образы и не пытается обновить их из registry.

Откройте `http://127.0.0.1:8080`. Логин преподавателя — `teacher`, начальный пароль
указан в `CAMPUS_TEACHER_PASSWORD` файла `.env`. Этот пароль задаётся только
при создании нового хранилища; изменение `.env` не меняет пароль существующего
аккаунта. Код группы доступен преподавателю в интерфейсе.

Если Docker работает на удалённом сервере, для первого знакомства используйте
SSH-туннель со своего компьютера:

```sh
ssh -L 8080:127.0.0.1:8080 user@server
```

Параметры вроде `user@server` заменяются реквизитами вашего сервера.
Для сервера с systemd Docker должен запускаться при загрузке ОС:

```sh
sudo systemctl enable --now docker
```

## Постоянная работа и данные

Compose запускает приложение и PostgreSQL с политикой `unless-stopped`.
Они восстанавливаются после сбоя процесса и перезапуска Docker, если ранее
не были остановлены вручную. После явного `docker compose stop` используйте
`docker compose up -d --wait`. Политика перезапуска относится к завершению
процесса; сама метка `unhealthy` не является командой Docker на перезапуск.

Приложение дожидается готовности PostgreSQL при запуске. Потеря владения БД
останавливает процесс приложения, чтобы Docker запустил его заново с актуальным
состоянием, сессиями и незавершённой очередью. Один экземпляр приложения
обслуживает одну БД; увеличение числа реплик не поддерживается.

Данные хранятся в named volume `campusjudge-server-postgres`, отдельно от
контейнеров и файлов выпуска. Не удаляйте volume при обновлении.
`docker compose down` сохраняет его; `docker compose down -v` удаляет данные.
Файл `.env` содержит пароли: сохраните его вместе с резервными копиями.
Журналы контейнеров ротируются, чтобы не расти бесконечно.

Команды выполняются из каталога с `compose.yaml` и `.env`:

```sh
docker compose ps
docker compose logs --tail=100 app
docker compose stop
docker compose up -d --wait
```

## Автопроверка и доступ к Docker

Приложение получает `/var/run/docker.sock` и запускает исполнителей в соседних
одноразовых контейнерах того же Docker daemon. Исполнитель уже включён
в архив: C++, C, Python, Go, Java и JavaScript не требуют установки на хост.
Входы передаются контейнерам через stdin; исходники не запускаются внутри
API-контейнера или непосредственно на сервере.

Доступ к Docker socket даёт приложению полномочия управления Docker-хостом.
Этот вариант рассчитан на отдельный сервер CampusJudge с доверенными
администраторами. API-контейнер не использует `privileged`; его файловая система
доступна только для чтения, capabilities сняты. Эти ограничения не отменяют
полномочий Docker socket. Socket и PostgreSQL не публикуются как сетевые порты.

Docker должен поддерживать cgroup v2 и ограничения памяти, swap, процессов
и CPU; иначе приложение откажется запускать автопроверку. Лимиты отдельных
решений задаёт существующий supervisor. Готовность к произвольной публичной
враждебной нагрузке не заявляется.

## Доступ через интернет

По умолчанию HTTP доступен только через `127.0.0.1:8080` хоста.
Для интернета настройте HTTPS reverse proxy перед ним. Прокси должен
перезаписывать `X-Forwarded-Proto` фактической схемой и передавать клиентский
адрес в `X-Forwarded-For`. В `.env` задайте `CAMPUS_TRUSTED_PROXIES` точным
CIDR адреса прокси, который видит контейнер приложения, и пересоздайте приложение:

```sh
docker compose up -d --wait app
```

Для прокси на Docker-хосте адрес может быть gateway сети Compose:

```sh
docker network inspect campusjudge-server_default --format '{{(index .IPAM.Config 0).Gateway}}'
```

Проверьте фактический адрес в вашей сети; не доверяйте `0.0.0.0/0`.
Если доступ нужен в доверенной локальной сети, измените
`CAMPUS_BIND_ADDRESS=0.0.0.0` и при необходимости `CAMPUS_PORT`.
Открывать HTTP с паролями напрямую в интернет не следует.

## Резервная копия и обновление

Для резервной копии используйте `pg_dump`, а не копирование работающего volume:

```sh
mkdir -p backups
docker compose exec -T postgres pg_dump -U campusjudge -d campusjudge -Fc > backups/campusjudge.dump
docker compose exec -T postgres pg_restore --list < backups/campusjudge.dump
```

Обе команды должны завершиться успешно. Проверяйте восстановление в отдельной
пустой базе по [руководству PostgreSQL](postgresql.md). Каталог `backups` и `.env`
не входят в публичный выпуск.

Для обновления скачайте и распакуйте новый архив в другой каталог, выполните
его `load-images.sh`. Затем в существующем каталоге установки:

1. Сделайте резервную копию БД и `.env`.
2. Остановите приложение: `docker compose stop app`.
3. Возьмите три значения образов из нового `release.env` и замените только
   `CAMPUS_APP_IMAGE`, `CAMPUS_RUNNER_IMAGE`, `CAMPUS_POSTGRES_IMAGE` в своём `.env`.
   Сохраните пароли, `CAMPUS_VOLUME_NAME`, bind-адрес и настройки прокси.
4. Обновите `compose.yaml`, `init-env.sh`, `load-images.sh` и инструкции из выпуска.
5. Выполните `docker compose up -d --wait` и проверьте вход и результаты учеников.

`init-env.sh` повторно не нужен. Обновление major-версии PostgreSQL требует
отдельного переноса БД; не меняйте major-тег поверх прежнего volume.
Откат приложения после изменения схемы может потребовать восстановление копии
в отдельный volume; совместимость старого бинарника с новой схемой не обещается.

## Сборка из исходников

Если готового архива для нужной архитектуры нет, клонируйте репозиторий
и соберите образы на Docker-сервере этой архитектуры:

```sh
docker build -t campusjudge:local .
docker build -f judge/Dockerfile -t campusjudge-runner:local .
docker pull postgres:17-alpine
cd deploy
./init-env.sh
docker compose up -d --wait
```

Это серверная конфигурация из `deploy/`. Корневой `compose.yaml` остаётся
вспомогательной БД для запуска Go-приложения с хоста.

Для подготовки скачиваемого выпуска из чистого коммита:

```sh
PLATFORM=linux/amd64 ./scripts/package-containers.sh v0.1.0
```

Для подготовки выпуска нужны Docker Buildx и BuildKit. Для ARM64 используйте
`PLATFORM=linux/arm64`; сборка другой архитектуры дополнительно требует
cross-platform execution на Docker-сервере. Скрипт проверяет архитектуру
каждого образа и создаёт архив и `.sha256` в `dist/`; секреты и рабочие данные
в них не копируются. Для локальной проверки незакоммиченных правок допускается
`ALLOW_DIRTY=1`, такой архив помечается `SOURCE_STATE=dirty`: указанный SHA
не описывает его исходники полностью. `SOURCE_COMMIT` чистого выпуска указывает
на исходный коммит; побитовая воспроизводимость образов не обещается, поскольку
обновления базовых образов и пакетов могут изменить результат сборки.
Публикация в GitHub Releases выполняется
отдельно после проверки; автоматического CI нет.
