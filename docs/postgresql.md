# PostgreSQL: запуск, перенос данных и контракт

## Выбор хранилища

Непустая переменная окружения `CAMPUS_DATABASE_URL` выбирает PostgreSQL. Без неё
сервер использует `data/state.json`, путь меняется через `-data`. Явный `-data`
при настроенной БД отклоняется, чтобы указанный файл не был молча проигнорирован.
Ошибка подключения или записи PostgreSQL не включает файловое хранилище.

Подключение передаётся через окружение, а не флаг командной строки. Go-сервер
не загружает `.env` автоматически; Compose читает этот файл для настройки
контейнера. Файл `.env` и рабочие данные исключены из Git.

## Локальный запуск с Compose v2

Нужны Go 1.25+ и Docker. При первом запуске из корня репозитория:

```sh
cp .env.example .env
docker compose up -d --wait
set -a
. ./.env
set +a
go run ./cmd/campusjudge -judge manual
```

Последняя команда запускает приложение без исполнителя решений. Для
автоматической проверки соберите runner по [руководству](automatic-judge.md)
и запустите ту же команду без `-judge manual`.

Пример использует `postgres:17-alpine`, базу и пользователя `campusjudge`,
порт `127.0.0.1:55432` и локальный пароль `campusjudge-local`. Перед работой
с данными занятий задайте свой пароль в `POSTGRES_PASSWORD` и обновите его
в `CAMPUS_DATABASE_URL`. В URL пароль должен быть корректно закодирован.
`sslmode=disable` в примере относится к локальному соединению.

Контейнер хранит данные в volume `campusjudge-postgres`. `docker compose stop`
останавливает базу, следующий `docker compose up -d --wait` запускает её снова.
Переменные инициализации PostgreSQL применяются только к новому volume: изменение
`.env` само по себе не меняет пароль пользователя в уже созданной БД.

На macOS нужен работающий Linux Docker: Docker Desktop или профиль Colima
из руководства исполнителя. При использовании Colima задайте
`export DOCKER_CONTEXT=colima-campusjudge` в той же оболочке.

## Запуск без Compose

Если плагина Compose v2 нет, используйте обычный Docker. Создайте `.env`
по примеру, затем выполните:

```sh
docker run -d --name campusjudge-postgres --env-file .env -e POSTGRES_DB=campusjudge -e POSTGRES_USER=campusjudge -p 127.0.0.1:55432:5432 -v campusjudge-postgres:/var/lib/postgresql/data postgres:17-alpine
docker exec campusjudge-postgres pg_isready -U campusjudge -d campusjudge
```

Дождитесь ответа `accepting connections` от второй команды; если база ещё
инициализируется, повторите проверку. Загрузите окружение и запустите приложение:

```sh
set -a
. ./.env
set +a
go run ./cmd/campusjudge -judge manual
```

Для повторного запуска созданного контейнера используйте
`docker start campusjudge-postgres`, для остановки —
`docker stop campusjudge-postgres`. Если меняете порт, измените одновременно
параметр `-p` и порт в `CAMPUS_DATABASE_URL`. Выберите один способ запуска базы;
не запускайте Compose и отдельный контейнер поверх одного volume одновременно.

## Перенос существующего JSON

Перенос выполняется отдельной командой, которая завершает работу после записи.
Она не запускает HTTP, Docker runner и начальное наполнение:

1. Остановите сервер, который использует прежний JSON. Сохраните отдельную
   резервную копию файла и сначала проверьте перенос на копии данных.
2. Подготовьте пустую БД и загрузите `CAMPUS_DATABASE_URL` в окружение.
3. Выполните из корня репозитория:

   ```sh
   go run ./cmd/campusjudge -import-json data/state.json
   ```

4. Запустите сервер обычной командой с той же `CAMPUS_DATABASE_URL`.
   Проверьте вход прежними аккаунтами, группы, задачи, посылки и историю результатов.

Импорт требует существующий корректный JSON поддерживаемой версии, получает
эксклюзивную блокировку его sidecar-файла и записывает целое состояние одной
транзакцией. Файл-источник не меняется; рядом может появиться `.lock`.
Непустое целевое хранилище отклоняется: повторный импорт не заменяет данные.
Пароли, хэши сессий, версии тестов, очередь и история вердиктов переносятся
вместе с остальными сущностями. Временные отметки нормализуются к UTC
с точностью до микросекунды.

Фактический символ U+0000 в тексте не поддерживается PostgreSQL: импорт
завершается ошибкой без изменения данных. Обычные текстовые последовательности
`\0` и `\u0000` в исходниках переносятся без изменений.

Для возврата к прежнему JSON остановите новый сервер, уберите
`CAMPUS_DATABASE_URL` из окружения и запустите файловый режим с сохранённым
файлом. Это возвращает состояние на момент переноса: изменения, сделанные
позже в PostgreSQL, в исходном JSON отсутствуют. Обратной синхронизации нет.

## Архитектурное решение от 23 ноября 2026 года

Прежний `Store.Update` атомарно менял всё доменное состояние и публиковал новый
снимок только после записи JSON. PostgreSQL добавлен как второй backend этого
контракта, чтобы сохранить существующие проверки доступа, очередь и HTTP API
без одновременного переписывания доменных сценариев.

Основные сущности размещены в отдельных таблицах схемы `campusjudge`:
пользователи, группы, темы, задачи, версии тестов, работы, связи работ,
посылки и сессии. Наборы тестов, ход проверки и история вердиктов используют
JSONB внутри соответствующей сущности. Драйвер — `pgx/v5`, ORM не используется.
Схема создаётся встроенными SQL-миграциями в транзакции при открытии БД;
версия схемы проверяется до загрузки состояния.

Одна операция `Store.Update` — одна транзакция PostgreSQL. Сохраняются изменённые
строки; остальные сущности не переписываются при каждом входе или вердикте.
Доменные правила продолжают работать с полным снимком в памяти. Обращения
к хранилищу сериализованы, а один worker по-прежнему проверяет решения
последовательно. Прямое редактирование таблиц при работающем сервере
не поддерживается, поскольку обходит этот снимок и доменные правила.

Один экземпляр приложения владеет одной базой через session advisory lock
на выделенном соединении. Второй экземпляр отказывается запускаться.
Это сохраняет правило единственного владельца очереди; добавление PostgreSQL
не означает поддержку нескольких API-серверов или распределённого исполнения.
Для такого перехода потребуется перенести чтение и захват заданий в БД
и отдельно определить конкурентное выполнение.

Разрыв соединения и неопределённый результат COMMIT требуют перезапуска
приложения: автоматическое переподключение могло бы продолжить запись из
устаревшего снимка после уже выполненного COMMIT или потери владения очередью.
Сервис проверяет соединение каждые пять секунд. При обнаружении разрыва или
неопределённого COMMIT дальнейшие записи блокируются, HTTP-сервис останавливается,
а процесс завершается с ошибкой. Политика перезапуска контейнера загружает БД
заново и восстанавливает незавершённую очередь. При запуске без менеджера
процессов приложение нужно запустить повторно вручную.

Альтернатива с одним JSON-документом внутри PostgreSQL не даёт явных связей
между сущностями. Полный переход HTTP-обработчиков на SQL-репозитории позволил
бы убрать общий снимок, но одновременно изменил бы границы доменных операций
и конкурентности. Он отложен до появления требования нескольких серверов
или измеренных ограничений текущего снимка.

## Резервная копия и восстановление

Для резервной копии PostgreSQL используйте `pg_dump`, а не копирование файлов
работающего volume. Пример для Compose:

```sh
mkdir -p data/backups
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > data/backups/campusjudge.dump
docker compose exec -T postgres pg_restore --list < data/backups/campusjudge.dump
```

Считайте копию готовой только после успешного завершения `pg_dump`; при ошибке
файл назначения может оказаться неполным. Архив содержит учётные данные
приложения и исходники решений, поэтому храните его вместе с рабочими данными.

Проверяйте восстановление в отдельной пустой базе. Для примера ниже имя
`campusjudge_restore` должно быть свободно; приложение должно быть остановлено:

```sh
docker compose exec -T postgres sh -c 'createdb -U "$POSTGRES_USER" campusjudge_restore'
docker compose exec -T postgres sh -c 'pg_restore --exit-on-error --single-transaction --no-owner -U "$POSTGRES_USER" -d campusjudge_restore' < data/backups/campusjudge.dump
```

Затем направьте `CAMPUS_DATABASE_URL` в `campusjudge_restore` и проверьте
сценарии приложения. Исходная база этими командами не заменяется. При прямом
запуске Docker вместо `docker compose exec -T postgres` используйте
`docker exec -i campusjudge-postgres`.

## Интеграционные проверки

Обычный `go test -race ./...` не требует PostgreSQL: проверки БД пропускаются,
если `CAMPUSJUDGE_POSTGRES_TEST_URL` не задана. Для них используйте отдельный
тестовый сервер PostgreSQL и роль с правом `CREATEDB`:

```sh
CAMPUSJUDGE_POSTGRES_TEST_URL='postgresql://postgres:test-password@127.0.0.1:55433/postgres?sslmode=disable' go test -race -count=1 -run Postgres -v ./internal/store ./internal/app ./cmd/campusjudge
```

Каждый тест создаёт собственную временную базу и удаляет её после завершения;
существующие базы не очищаются. Тесты проверяют транзакции, импорт, перезапуск,
права доступа, сессии и восстановление очереди. HTTP-проверки используют
управляемый исполнитель и не требуют Docker runner.
