# Журнал разработки

## Шаг 1 — постановка и архитектура

- Зафиксированы темы, домашки, контесты и роли преподавателя и ученика.
- Выбраны Go, локальное файловое хранение и интерфейс без обязательного Node.js.
- БД и CI исключены по текущему запросу.
- До готовности изолированной среды посылки требуют ручной проверки.

Проверено: документы согласованы с текущим запросом; исходники, секреты,
личные данные и учебные решения в начальный коммит не включены.

## Шаг 2 — рабочее ядро на Go

- Добавлены аккаунты, приглашения в группы и серверное разделение ролей.
- Темы содержат внешнюю ссылку на видеозанятие; они доступны до открытия домашки.
- Реализованы задачи, публикация работ, приём исходников, ручная проверка и таблица.
- Состояние сохраняется в JSON через атомарную замену с откатом при ошибке.
- Начальные данные ограничены тестовой домашкой и контестом, без выдуманных учеников.

Проверено: `go test -race ./internal/... ./cmd/...`, `go vet ./internal/... ./cmd/...`.
HTTP-тест проходит путь «тема → черновик → регистрация → публикация → посылка →
проверка → повторное открытие хранилища». Дополнительно проверены чужая группа,
скрытые тесты, права ученика, границы времени и независимый расчёт штрафа.
Независимое ревью выявило скрытие ссылки на урок до публикации домашки; исправлено,
этот сценарий включён в тест. Интерфейс браузера ещё не входит в этот шаг.

## Шаг 3 — отделение правил от транспорта

- Правила работы, видимости, временных границ и таблицы перенесены в чистый
  `internal/domain`; HTTP-обработчики вызывают их внутри транзакций.
- Ответ с состоянием класса стал типизированной проекцией для текущей роли.
- Уровень доступа объявляется у маршрута именованным значением вместо двух bool.
- Начальный пароль и время передаются при инициализации явно; чтение окружения
  осталось в точке запуска. Ошибки хеширования возвращаются вызывающему коду.
- Функциональность и формат API сохранены; ранее записанные файлы продолжают читаться.

Проверено: прежние HTTP-сценарии, `go test -race ./internal/... ./cmd/...`,
`go vet ./internal/... ./cmd/...`; независимое ревью сопоставило JSON-контракты
и транзакционные границы. Замечание о дублирующемся ограничении роли в HTTP
устранено: допуск посылки определяет `domain.CanSubmit`.

## Шаг 4 — модульный интерфейс преподавателя и ученика

- Добавлены разные экраны и действия для двух ролей, создание тем, групп, задач,
  домашних заданий и контестов; публикация и ручная проверка с обратной связью.
- Frontend разделён на нативные ES-модули с явными зависимостями: HTTP, состояние,
  построение команд форм, контроллер эффектов, компоненты и представления.
- Весь интерфейс встраивается в Go-бинарник без сборки. HTTP не выдаёт файлы Go,
  тестов, рабочего состояния и каталоги модулей.
- Асинхронные ответы привязаны к поколению сессии и актуальному запросу снимка.
  Изменения cookie через вход/выход выполняются последовательно.

Проверено: `go test -race ./...`, `go vet ./...`, 28 Node-тестов без зависимостей.
Независимое ревью проверило разделение ответственности и ошибки порядка ответов;
замечания исправлены и закреплены управляемыми асинхронными тестами.

В браузере пройдены создание темы со ссылкой, создание черновика и открытие доступа,
регистрация ученика, отправка кода, ручная проверка и показ комментария ученику,
сохранность после перезапуска, таблица контеста и мобильное меню при ширине 390 px.
Финальная версия повторно запущена с чистым отдельным хранилищем: только две
тестовые работы, без учеников, тем, посылок и вымышленных результатов. Ошибок
в журнале браузера при проверке не обнаружено. Автоматический запуск кода пока
отсутствует; ручной режим явно обозначен в интерфейсе и README.

## Шаг 5 — исследование учебных интерфейсов

Сопоставлены публичные экраны Codeforces и AtCoder, официальные материалы Canvas,
Google Classroom, Moodle, Stepik, Eolymp и Яндекс Контеста. Доступ к частным
кабинетам не использовался. Источники, ограничения просмотра и решения сохранены
в [сравнении интерфейсов](interface-research.md) отдельным коммитом.

## Шаг 6 — минималистичный рабочий интерфейс

- Убраны рекламная часть входа, приветственные слоганы, KPI-плитки, декоративные
  аватары и повторные анонсы контеста. Навигация перенесена в верхнюю часть.
- Обзор и списки используют общую таблицу работ: название, группа, задачи, срок,
  состояние и прогресс. У преподавателя отдельная очередь проверки, у ученика —
  собственные последние результаты.
- Темы и группы представлены списками. Условие и отправка кода, исходник и форма
  проверки находятся рядом на широком экране и друг под другом на узком.
- Для новой ручной проверки нужно явно выбрать вердикт; ранее выставленный
  результат сохраняется выбранным. Добавлена регрессионная проверка этого поведения.
- Backend, API, файловое хранение и набор начальных данных сохранены.

Проверено: 29 Node-тестов, `go test -race ./...`, `go vet ./...`, статическое
независимое ревью. В браузере пройдены создание темы со ссылкой, черновик и открытие
домашки, регистрация, отправка исходника Go, явный выбор результата, комментарий
ученику и таблица контеста. На ширине 320 px проверены меню и отсутствие лишней
прокрутки всей страницы; широкие таблицы прокручиваются внутри своего контейнера.
Найденное переполнение панели поиска исправлено и повторно проверено. Ошибок в
журнале браузера при этих сценариях нет. Рабочие данные не используются как тестовые:
QA выполнялась с отдельным временным JSON-файлом.

## Шаг 7 — контракт автоматической проверки

До реализации опубликован отдельный [план](automatic-judge.md): Linux-контейнеры,
сохраняемая очередь, шаблоны, темы и живая обратная связь. БД и CI не добавляются.

## Шаг 8 — изолированный исполнитель

- Добавлены Docker runner, доверенный Linux supervisor и образ с C++, C, Python,
  Go, Java и JavaScript. Код ученика выполняется с uid/gid 65534 без capabilities.
- Сеть отключена, root read-only, рабочие данные находятся только в ограниченных
  tmpfs. Ограничены процессы, CPU, память без swap, время и вывод. Ожидаемые ответы
  не передаются контейнеру; сравнение по токенам выполняет доверенный Go-код.
- Каждая компиляция и тест изолированы, артефакты передаются ограниченным пакетом
  в памяти. Контейнеры убираются при завершении и отмене, внутренний watchdog
  ограничивает жизнь даже при обрыве API до полной передачи stdin.
- `.dockerignore` исключает из build context рабочие данные и остальные файлы.

Проверено: host unit/race и vet; Linux unit-тесты внутри сборки; реальный Docker
на отдельной Colima VM без host mounts. Все шесть языков получили Accepted;
отдельно получены WA, CE, RE, TLE, MLE и OLE. Проверены отсутствие capabilities
у решения, недоступность supervisor stdout, запрет сети/записи в root, cgroup
limits, новый workspace на тест и удаление контейнера после отмены.

Реальная проверка бесконечного цикла выявила, что root supervisor без KILL не
может остановить процесс другого uid. Ему оставлены только SETUID, SETGID, KILL;
у решения capabilities нулевые. После исправления весь интеграционный набор
прошёл. Неполный stdin завершился по внутреннему watchdog с кодом 70 за 45,22 с.
Это проверка ограничений локального runner, а не заявление об изоляции уровня
публичного Codeforces.

## Шаг 9 — сохраняемая очередь и язык API

- Посылка и queued записываются одной транзакцией. Worker исполняет задачу вне
  блокировки хранилища и сохраняет результат условно, не перезаписывая ручной.
- Незавершённые задания продолжаются после перезапуска. Повтор записи результата
  при ошибке диска не запускает исходник заново. Очередь ограничена глобально и
  на ученика; старые ручные посылки автоматически не принимаются в исполнение.
- API возвращает возможности языков, полные шаблоны и публичные поля результата.
  Источник ограничен одинаковыми 128 КиБ в браузере, API и executor. Нет тестов —
  отказ до постановки в очередь. judge_error исключён из штрафа контеста.
- CLI включает Docker judge по умолчанию; явный `-judge manual` не требует Docker.
  Старые JSON-файлы читаются, поля проверки копируются без изменяемых общих ссылок.

Проверено: `go test -race -count=1 ./...`, `go vet ./...`, сборка бинарника.
Тесты охватывают полный HTTP lifecycle, восстановление running, приоритет ручного
результата, лимиты очереди, отсутствие тестов, превышение source limit, неполный
результат runner и отказ инфраструктуры. С настоящим runner пройден путь через
браузер: C++ source → running → Accepted, 3 из 3 тестов, без ручной перезагрузки.
Новые проверки используют отдельный временный JSON, рабочее пространство не меняют.

## Шаг 10 — редактор, темы и обратная связь

- Рабочая область упрощает компоновку публичного LeetCode: условие слева,
  редактор и вкладка результата справа; свои стили, без чужих ассетов.
- Светлая/тёмная тема сохраняет выбор. Полные шаблоны берутся из каталога API,
  а непустой код заменяется только после явного подтверждения.
- Черновики и язык сохраняются отдельно по пользователю, работе и задаче.
  Тихий опрос обновляет результат, сохраняя редактор и незавершённые формы.
- Ревью выявило потерю polling после BFCache и смешение старого редактора с новым
  аккаунтом после смены cookie в другом табе. Обе границы исправлены и проверены.
  Сравнение времени последних посылок учитывает дробные секунды RFC3339Nano.

Проверено: 48 Node-тестов без зависимостей, граф импортов и выдача встроенных
модулей Go-сервером. В браузере реально пройдены C++ Accepted, C++ Compilation
Error с диагностикой, Python Wrong Answer и повторный Python Accepted — без
ручного обновления. Исходник сохраняется после отправки и смены вкладки;
черновики разных языков и тема восстанавливаются после перезагрузки.

На 320 px найдено и исправлено обрезание кнопки шаблона: содержимое toolbar
теперь равно доступной ширине, 188/188 px. На обычном экране кнопка отправки
полностью видна; временный mobile viewport сброшен. Основное пространство
сохраняется отдельно от QA-ученика, его посылок и результатов.
